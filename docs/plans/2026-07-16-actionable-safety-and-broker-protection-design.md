# LumaNest 可执行安全预警与 Broker 基础保护设计

## 目标

修复 V1 中官方气象预警只显示通用标题的问题，并为公网 Broker 增加可在 NAS 上运行的基础限流。安全事实、预警等级和规避动作保持确定性，不交给 AI。

## 兼容策略

`ContextSnapshotV2` 保持原有响应字段，避免旧 APK 的严格解析失败。Broker 从和风预警中保留一个受限标题，FastAPI 将其写入现有 `ContextEvent.title`，因此旧客户端也会在安全卡上看到具体预警名称。

新客户端在用户打开安全卡时，使用已有 `contextId` 与事件 ID 调用新增的受保护详情接口。详情只在 Broker 的短 TTL 内存或 Redis 缓存中保存，返回官方说明、确定性规避动作、来源和有效时间；缓存未命中时客户端继续显示本地模板。请求、缓存键和日志不得保存精确坐标、服务令牌或原始模型内容。

## 数据流

```text
QWeather warning → Broker 归一化标题、说明、类型、等级
                → FastAPI 生成 V2 安全事件标题
                → Flutter 安全卡
                → 点击后 Broker safety-detail → 官方说明 + 规则动作
```

规避动作由 Broker 的受限类型/等级映射生成；未知类型只返回通用的“减少户外暴露、关注官方更新”动作。原始预警说明会去除换行、限制长度，不能包含可执行链接或模型生成内容。

## 保护策略

Broker 在所有已鉴权的 `/v1/*` 端点前执行固定窗口限流。键由端点和 SHA-256 截断后的 socket 来源组成；不信任可伪造的转发头。Redis 可用时使用 Redis 计数和 TTL，不可用时退回进程内计数，保证保护不会因 Redis 故障消失。命中上限返回 `429`、`Retry-After` 与稳定错误码，不回显身份信息。

首轮限制区分高费用端点：AI 文案最低，GBIF 次之，天气/地图较高。全局限流并不把嵌入 APK 的服务令牌当作秘密；后续仍需引入安装级短期令牌或应用证明。

## 验证

- Node：和风标题/说明清洗、详情缓存、未知预警回退、每类端点限流、Redis/内存回退。
- FastAPI：官方预警标题进入 V2 事件且旧响应字段不变。
- Flutter：安全卡显示具体标题；详情成功、缓存未命中和非法详情均回退本地模板。
- 回归：Flutter analyze、Flutter 全量测试、Node 全量测试、FastAPI 全量测试、格式与 diff 检查。
